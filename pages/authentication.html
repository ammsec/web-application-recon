Authentication

Once endpoints and parameters are mapped, look at how the target actually verifies identity — login flows, session tokens, and authorization checks are where some of the highest-impact bugs live.

Why this phase matters

A broken auth flow can undermine every other security control on the site. Weak session tokens, a JWT that isn't properly verified, or a password reset flow with a predictable token can turn into full account takeover — often with far less effort than finding an injection bug.

JWT Analysis

jwt_tool Python

What it does: Decodes, tampers with, and attacks JSON Web Tokens — checks for weak signing secrets, the classic alg: none bypass, and key confusion between RS256 and HS256.

GitHub ↗

Installation

git clone https://github.com/ticarpi/jwt_tool.git
cd jwt_tool
pip3 install -r requirements.txt

Usage

# Decode a token and inspect header/payload
python3 jwt_tool.py <JWT>

# Run all known attack modes automatically
python3 jwt_tool.py <JWT> -M at

# Try the alg:none bypass
python3 jwt_tool.py <JWT> -X a

# Crack a weak HMAC secret with a wordlist
python3 jwt_tool.py <JWT> -C -d /usr/share/seclists/Passwords/xato-net-10-million-passwords.txt
Manual JWT Checklist Checklist

Even without a tool, a few quick manual checks catch common misconfigurations:

# Decode header + payload manually — no signature needed
echo <base64-header> | base64 -d
echo <base64-payload> | base64 -d

# Things to check:
# - Is "alg" set to "none" accepted by the server?
# - Does the token expire (exp claim present and enforced)?
# - Can "kid" or "jku" headers be manipulated to point at an attacker-controlled key?
# - Is the signature actually verified, or just decoded?

Session & Cookie Checks

Cookie Attribute Review Manual

Inspect session cookies via browser dev tools or a proxy (Burp/ZAP) and confirm the basics are actually set:

# Look for these attributes on session cookies:
# HttpOnly   - blocks JS access, mitigates session theft via XSS
# Secure     - cookie only sent over HTTPS
# SameSite   - Lax/Strict, mitigates CSRF
#
# Also worth checking:
# - Does the session token stay valid after logout?
# - Is the token predictable (sequential IDs, low entropy, timestamp-based)?
# - Does changing the password invalidate other active sessions?

Login Flow & Brute Force Testing

ffuf — Credential & Rate-Limit Testing Go

What it does: The same fuzzer from the directory phase works well for testing login endpoints — default credentials, username enumeration via response differences, and whether rate limiting actually kicks in.

Usage

# Test a small list of default/common credentials — never brute force real accounts without authorization
ffuf -u https://target.com/login -w creds.txt -X POST \
  -d "username=admin&password=FUZZ" -fc 401

# Check for username enumeration via response length/timing differences
ffuf -u https://target.com/login -w usernames.txt -X POST \
  -d "username=FUZZ&password=wrongpass" -fs 1234

OAuth / SSO Misconfigurations

Common things to check

If the target uses OAuth or an SSO provider, check whether the redirect_uri parameter is validated against a strict allowlist (open redirect here can lead to token theft), whether the state parameter is present and unpredictable (missing state enables CSRF on the auth flow), and whether tokens are scoped correctly instead of granting broader access than the requesting app needs.
